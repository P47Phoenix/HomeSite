## Context

HomeSite is a LAN-only static landing page served from a Talos Kubernetes cluster (Raspberry Pi ARM64 workers) behind ingress-nginx and a MetalLB L2 VIP. The site must serve HTTPS with fully automated certificate issuance and renewal (PRD FR-12, NFR-3, NFR-4), with no credentials in git (FR-15a), no paid or new SaaS dependencies (FR-15b), and no scheduled manual operations (FR-15c). The operator is a solo home-lab maintainer with an explicit self-healing bias.

The binding constraint is PRD FR-12, hardened at v1.2 by an accepted HIGH-severity adversarial finding (F2): the certificate must chain to a root trusted by **factory-default browsers on household devices — zero per-device trust installation**. A local-CA alternative is permitted only via an escape hatch requiring explicit operator sign-off recorded as a PRD assumption change, with the per-device installation cost stated.

Relevant environment facts (verified against repo evidence in the architecture document):

- The site is LAN-only; inbound ACME HTTP-01 is unavailable by construction (no port exposure to the internet).
- The Route53 zone `theconnellyfamily.info` already exists, is already paid for, and carries live DDNS automation — no new SaaS or cost is introduced by using it (PRD D7).
- cert-manager is NOT currently installed on the cluster (archived snapshot evidence corrected an earlier docs-only claim); installation is required under **either** candidate and is therefore not a differentiator.
- The hostname decision (public DNS name `homesite.home.theconnellyfamily.info` resolving to a private ingress VIP — architecture §5 Option A) is forced independently by the resolver-agnostic requirement (F13): split-horizon DNS fails devices pinned to public resolvers outright. DNS-01's public-DNS prerequisite is therefore already satisfied by a decision made on its own merits.
- The repo has no existing sealed-secrets/SOPS practice; a sealed-secrets controller is new infrastructure introduced by this decision.

The decision was contested and resolved by structured debate (PRO/CON arguments plus judgment recorded at `.delivery/artifacts/04-architect/debate-judge/decision.md` in the Containers repo).

## Decision

We will issue and renew HomeSite's TLS certificate using **ACME DNS-01 against Let's Encrypt, via cert-manager with the Route53 DNS-01 solver**, on the existing `theconnellyfamily.info` hosted zone.

Concretely:

1. Install cert-manager from the already-declared jetstack Helm repository — chart version pinned to **`v1.21.1`**, values committed at `helm/releases/cert-manager/values.yaml` with `installCRDs: true` (CRDs lifecycle-managed with the release). The `!helm/releases/` gitignore fix is a sequenced blocking prerequisite of this values commit (architecture §2 Step 0), not parallel hygiene.
2. Create a dedicated IAM user whose policy contains **exactly two statements** *(amended 2026-07-31 per security review SEC-01 — the original "both actions scoped to the single hosted zone" wording was incorrect: `route53:GetChange` cannot be zone-scoped; its resource is `arn:aws:route53:::change/*`. The amended policy also adds condition keys that shrink the blast radius from "tamper any record in the zone, including the live DDNS record" to "write ACME challenge TXT records only")*:
   - Statement 1: `route53:GetChange` on `arn:aws:route53:::change/*`.
   - Statement 2: `route53:ChangeResourceRecordSets` on `arn:aws:route53:::hostedzone/<ZONE_ID>` with conditions `ForAllValues:StringEquals route53:ChangeResourceRecordSetsRecordTypes = ["TXT"]` and `ForAllValues:StringLike route53:ChangeResourceRecordSetsNormalizedRecordNames = ["_acme-challenge.*"]`.
   - No other statements. Dev verifies condition-key behavior against current AWS docs plus the four-case live test matrix in Conditions (loop-2 m-4: denied A-record change; denied TXT at a non-`_acme-challenge` name; **allowed** TXT at `_acme-challenge.*` as the explicit positive case; `ForAllValues` empty-key-set vacuous-true edge checked) before the key is sealed.
3. Deliver the IAM credential to the cluster as a Bitnami sealed-secrets `SealedSecret` committed to the Containers repo (ciphertext in git; decryptable only by the cluster), keeping the deploy fully reproducible from git.
4. Define an ACME `ClusterIssuer`/`Issuer` (staging endpoint first, then production) and a `Certificate` for the site hostname; ingress-shim manages the TLS Secret consumed by ingress-nginx. The route53 solver sets `hostedZoneID: <ZONE_ID>` explicitly so `route53:ListHostedZonesByName` is never called and never granted (security review SEC-02).
5. Alert on renewal failure via dual instrumentation: blackbox `probe_ssl_earliest_cert_expiry` (mechanism-independent) and `certmanager_certificate_expiration_timestamp_seconds`, both with a 21-day threshold, test-fired before UAT with a short-lived test Certificate (no backdating).

### Conditions and required mitigations

The following obligations are part of this decision (each traces to a surviving point from the rejected alternative's argument):

- **Least-privilege IAM verified**: the attached policy is read back and recorded as evidence at Dev before the credential is sealed; it must match the amended two-statement shape in Decision step 2 exactly (SEC-01), including the TXT-type and `_acme-challenge.*`-name condition keys. Verification is a **four-case live test matrix (amended per loop-2 m-4 — a single negative case did not distinguish the name condition from the type condition)**: (1) A-record change → AccessDenied; (2) TXT write at a non-`_acme-challenge` name (e.g. `TXT home.theconnellyfamily.info`) → AccessDenied; (3) TXT write at `_acme-challenge.<site label>` → **allowed** (explicit positive proof before first issuance); (4) the documented `ForAllValues` vacuous-true edge checked (AWS warns `ForAllValues` + Allow evaluates true on an empty condition-key set). All four results committed as evidence with the policy read-back.
- **CAA issuance pinning (SEC-03; scope amended per loop-1 F-6)**: a CAA record on the **site label** — `homesite.home.theconnellyfamily.info` (or the label chosen at sign-off) `issue "letsencrypt.org; validationmethods=dns-01; accounturi=<operator ACME account URI>"` — is recorded after first production issuance (`dig CAA <label>` output logged as evidence). **NOT at the zone apex**: CAA inheritance means an apex `accounturi` pin would silently refuse issuance for every other present or future certificate in `theconnellyfamily.info` — any other CA, any other ACME account (TrueNAS/UniFi/router built-in clients always use their own), any non-DNS-01 validation — turning this project into an undocumented gatekeeper for a shared family zone, with failures surfacing months later as unexplained CAA errors. Label-scoping still closes the threat this condition exists for: the stolen scoped key can only write `_acme-challenge.*` TXT records, and the label CAA denies it a usable issuance path for this hostname without the ACME account key (held in a different cluster Secret). If the operator later prefers apex-wide pinning, that is a separate zone-governance decision with a mandatory "adding any other certificate in this zone requires touching this CAA record" operational note. **Compensating zone-level control (amended per loop-2 M-1 — label-scoping left every un-pinned zone name a live issuance path for the stolen key):** in the same first-issuance DNS change set, a **zone-apex CAA `issue "letsencrypt.org"` WITHOUT `accounturi`** is recorded. Inherited by every name lacking its own CAA record (including `home.theconnellyfamily.info`), it blocks all non-Let's-Encrypt CAs zone-wide while never gatekeeping family ACME clients that use Let's Encrypt — the F-6 apex hazard came from pinning `accounturi` at the apex, not from naming the CA. The remaining residual (stolen key completing *Let's Encrypt* issuance for un-pinned names) is an explicit Sign-off checklist acceptance with its blast radius stated. **Zone-governance operational note (loop-3 F3-3 — the F-6 standard applies to this record too):** the apex `issue` record is a zone-wide gate of the same class as the rejected apex `accounturi` pin, only diluted — it silently refuses issuance for every present or future certificate in `theconnellyfamily.info` from any CA other than Let's Encrypt, and widely deployed ACME clients do **not** default to Let's Encrypt (`acme.sh`, embedded in many NAS/router firmwares, has defaulted to **ZeroSSL** for years; appliance clients variously use ZeroSSL, Buypass, or vendor CAs) — precisely the "failures surfacing months later as unexplained CAA errors" scenario the F-6 analysis condemned. Mandatory rule, recorded here and in the DNS runbook: **adding any certificate in `theconnellyfamily.info` from a CA other than Let's Encrypt requires editing the apex CAA record first; before configuring any new ACME client (TrueNAS/UniFi/router/NAS), check which CA it defaults to.** Both CAA records (and the site A record) have a committed representation at `dns/homesite-records.json` in the Containers repo (architecture §5, loop-3 F3-7), so zone state rebuilds from git, not memory. Evidence after first issuance: `dig CAA <site label>` AND `dig CAA theconnellyfamily.info`. **Wildcard interaction (amended per loop-2 m-3):** for a wildcard certificate the CAA relevant set is evaluated at `home.theconnellyfamily.info` and above — the label pin at the site hostname never applies; adopting the wildcard mitigation therefore REQUIRES re-placing the CAA pin at `home.theconnellyfamily.info` with `issuewild` semantics addressed, or the SEC-03 control is silently exited.
- **Credential rotation runbook**: rotation = rotate access key + re-seal one SealedSecret + commit; documented with explicit triggers (suspected exposure; optional operator-chosen cadence). Not a scheduled required step; the 21-day expiry alert is the backstop that surfaces a dead credential well inside the renewal window.
- **Sealing-key DR (amended per loop-1 F-5 — "one-time" was wrong)**: the sealed-secrets controller rotates its sealing key every 30 days by default, and this ADR's own rotation runbook re-seals ciphertext — so a one-time backup stops covering the committed SealedSecret after the first rotation, silently voiding the rebuild-from-git guarantee. Corrected obligation: the backup into the operator's secret store is refreshed with **all** sealing keys as the **final step of every seal/re-seal operation** (`kubectl get secret -n kube-system -l sealedsecrets.bitnami.com/sealed-secrets-key -o yaml`); the initial backup is verified restorable once; controller key rotation stays at the default (disabling it was considered and rejected — it concentrates risk on git-hosted ciphertext to rescue a wording). This standing rule is the precondition for the rebuild-from-git guarantee.
- **DNS-rebind fallback**: the reachability drill tests ≥2 LAN clients with distinct resolver configurations; if router-DNS clients fail due to rebind protection dropping RFC1918 answers, apply the documented one-time UniFi allow-list exception and re-verify it after router firmware updates or factory resets.
- **CT-log/public-DNS disclosure acceptance**: the hostname and private IP appearing in public DNS and Certificate Transparency logs must be accepted by explicit operator sign-off (Sign-off checklist above — currently pending; informational disclosure only; LAN-only service, no inbound path). A wildcard certificate (`*.home.theconnellyfamily.info`) is the documented mitigation if the specific label should later be hidden from CT logs — same issuer, no redesign, **but wildcard adoption requires re-placing the CAA pin at `home.theconnellyfamily.info` with `issuewild` (loop-2 m-3; see the CAA condition above) — the label-scoped pin never applies to a wildcard**.
- **Secret-bootstrap contingency (carried in from architecture §7 per loop-1 F-14 — this ADR owns it)**: if the operator vetoes the sealed-secrets controller at Plan, the sanctioned fallback is a documented one-time `kubectl create secret` bootstrap of the Route53 credential, with its stated cost accepted: the deploy is then NOT fully reproducible from git alone and the secret dies with the cluster (FR-14/NFR-11 partially waived, recorded as a PRD assumption change). Invoking the fallback is an amendment note to this ADR, not a re-debate; the DNS-01 decision itself is unaffected.

## Consequences

### Positive

- FR-12 is satisfied as written: every household and guest device trusts the certificate out of the box, with zero per-device installation, permanently. Story 4 (no browser certificate warnings for non-technical visitors) holds with no operator support-desk role.
- Renewal is fully automated on a 90-day cadence with battle-tested cert-manager machinery, proven by a forced-renewal drill (zero manual steps), a real-renewal observation at ~day 60, and a test-fired 21-day expiry alert — renewal failure is loud, early, and leaves a 30+ day human-response buffer.
- Zero new cost and zero new vendors: the Route53 zone, the jetstack Helm repo, and GitHub tooling are all pre-existing.
- Secret handling improves on the repo's prior de-facto pattern (secrets in gitignored values files): the SealedSecret ciphertext lives in git and the deploy remains reproducible from the repo alone.
- If the site is ever publicly exposed (the identified volatile axis), the certificate and issuer work unchanged — no TLS rework.

### Negative

- A standing cloud credential lives in the cluster to serve roughly 4–6 renewal events per year. With the amended SEC-01 policy, its theft enables writing `_acme-challenge.*` TXT records only — it can no longer touch the live DDNS A record — but that is still sufficient to complete DNS-01 issuance for zone names. **Corrected per loop-2 M-1 (the prior "which the SEC-03 CAA `accounturi` pin closes" claim became false after amendment 2's label re-scope):** the label-scoped pin closes the issuance path only for the site hostname; every other zone name without its own CAA record — including the live DDNS endpoint `home.theconnellyfamily.info` — remained a live issuance path, with a valid mis-issued certificate for the operator's real WAN hostname as the blast radius. The zone-apex CAA `issue "letsencrypt.org"` floor (no `accounturi`; see Conditions) narrows that residual to Let's-Encrypt-only issuance, and the remainder is an explicit Sign-off checklist acceptance. Bounded by least-privilege scoping plus condition keys, sealed-at-rest delivery, and a single-action rotation path — but it is a 24/7 exposure that the local-CA alternative would not have had.
- Certificate renewal depends on outbound reachability of Let's Encrypt and the Route53 API. The TLS/serving components are unaffected by their outages; an outage must persist through most of the ~30-day renewal window before TLS is impacted, and the 21-day alert fires first. **Precision added per loop-1 F-2:** "serving path unaffected" holds for TLS and content, but the serving path's *first hop* — resolving the public-DNS-only hostname — is WAN-dependent: during a WAN outage, LAN clients lose resolution after DNS TTL expiry. That coupling is a consequence of the hostname scheme (architecture §5), where it is now documented as an explicitly accepted availability exclusion (TTL 300; optional UniFi local-record degraded path), and appears on the Sign-off checklist.
- The internal hostname and its RFC1918 address become permanent public records in DNS and CT logs (accepted disclosure, wildcard mitigation available).
- New moving parts on-cluster: cert-manager (required either way) plus the sealed-secrets controller and its sealing-key DR duty (specific to this path).
- Renewal cadence is subject to external policy (Let's Encrypt lifetimes, CA/Browser Forum lifetime reductions). The renewal path being automated absorbs the cadence change, but the **alarm does not** (loop-1 F-12): the 21-day thresholds assume 90-day lifetimes (cert-manager renews at 2/3 lifetime); at lifetimes ≤ ~63 days the healthy renewal point lands inside 21 days and the cert alerts would fire on every good cycle. Mitigation is the pinned invariant in architecture §6 — **alert threshold < lifetime/3, reviewed whenever issued-certificate lifetime changes** — so a lifetime reduction triggers a threshold review instead of a perma-firing alert.

### Neutral

- Requires the public-DNS-to-private-IP hostname scheme — already independently chosen to satisfy resolver-agnostic resolvability, so this decision adds no new DNS constraint.
- Expected router rebind-protection exception on the UniFi gateway (router DNS + rebind protection are UniFi defaults, so the reachability drill is planned to need it): a documented setup step with an event-triggered re-verify obligation after router firmware updates or factory resets (per Conditions) — not a scheduled recurring operation (loop-1 F-13 alignment).

## Alternatives Considered

| Alternative | Pros | Cons | Reason Rejected |
|-------------|------|------|-----------------|
| Local CA (cert-manager CA issuer, self-managed root) | Zero external dependencies (fully offline renewal path); no cloud credential anywhere; hostname unconstrained; no CT-log disclosure | Fails FR-12 as written — no factory-default browser trust; requires root installation on every household device (~8–15), recurring for each new/guest device and impossible on some TV/IoT browsers; root rotation is an unalarmed, manual, per-device-touching event a decade out (violates NFR-4's zero-manual target); CA root key compromise would poison trust on every household device until manually removed device-by-device — a strictly larger blast radius than a zone-scoped IAM key | Dispositive: the FR-12 escape hatch requires explicit operator sign-off that was not sought or granted; even beyond FR-12, it loses on renewal automation, blast radius, and the recurring per-device toil placed on non-technical household members |
| ACME HTTP-01 (Let's Encrypt) | No DNS credential; simplest ACME solver | Requires inbound HTTP reachability from the public internet; the site is LAN-only with no port exposure | Unavailable by construction (PRD Section 7 scope) |
| No TLS / plain HTTP | No cert machinery at all | Violates NFR-3 (HTTPS everywhere) and FR-12 outright | Not a lawful option under the PRD |
